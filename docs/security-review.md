# Module 5 Security Review

This review grades the supplied AI findings against the current repository. The
proposed grades are advisory; the student retains the final decision.

| Finding ID | Proposed grade | Reason | Evidence needed or evidence used | Student decision to confirm |
|---|---|---|---|---|
| SEC-01 | Valid | `description` and `assignee` accept arbitrary-length strings on both create and update paths, while all matching tasks are materialized and returned without a limit. This is a credible availability/resource-use limitation outside the small in-memory course setting. | Verified in `app/models.py`: only `title` has a validator and 200-character cap. Verified `storage.get_all_tasks()` returns the full matching list; `GET /tasks` exposes no pagination parameters. | Confirm whether the API is expected to remain local/small-data only. If yes, record it as an accepted course-scope limitation; otherwise add limits and pagination. |
| SEC-02 | Valid | The API has no authentication or task ownership checks, so any reachable caller can read, create, modify, or delete tasks. The repository explicitly makes this an intentional course constraint, so it is not an implementation defect within the assignment, but remains a production deployment risk. | Verified all CRUD handlers in `app/main.py` lack identity/authorization logic. `app/CLAUDE.md` explicitly says not to add authentication. | Confirm the deployment boundary: local/course-only makes the limitation accepted; shared or internet-reachable deployment requires separately approved authentication and authorization work. |
| SEC-03 | Valid | This is accurately framed as a deployment-configurability limitation, not permissive CORS. The fixed localhost origins and HTTP API URL prevent normal non-local deployment and would need environment-specific configuration and HTTPS. | Verified `app/main.py` permits only the two local Live Server origins. Verified `app/frontend/index.html` sets `baseUrl` to `http://localhost:8000`. | Confirm whether non-local deployment is in scope. If not, accept as course-only configuration; if yes, make origins and the base URL configurable. |
| SEC-04 | Valid | The concrete mutable Docker base tags are a real reproducibility/supply-chain control gap: later builds can consume a different image without a repository change. The lack of scanning is a reasonable production hardening observation, though it does not demonstrate a known vulnerable dependency or compromise. | Verified both Docker stages use mutable `python:3.11-slim`; CI only installs dependencies and runs tests. `requirements.txt` pins direct Python dependencies. | Confirm whether CI/container delivery is production scope. If yes, pin reviewed base-image digests and add the organization's chosen dependency/container scanning; otherwise treat it as an accepted course-scope limitation. |
